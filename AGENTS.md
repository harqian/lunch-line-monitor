# lunch_line_monitor

camera -> person detection (YOLO26n) -> live count + box positions on https://nuevasocratica.com/lunch-line-monitor. target hardware: raspberry pi + arducam mini 2mp plus (OV2640, spi + i2c). each update is `{count, people:[{box, confidence}], frame_width, frame_height, jpeg (base64)}`; the page shows the live frame with boxes (changed from faceless figures on 2026-10-08 at Harrison's request). privacy (Eric Spross, Director of Technology, 2026-11-12: approved on the condition of "no livestreaming or recording of identifiable people", minimal access to the raw feed, and tech department access to the back end): the raw frame never leaves the pi. the camera sends `jpeg` = whole frame pixelated in 14 px blocks (20 until 2026-11-16, Harrison) (`pixelated_jpeg` in stream_people.py) plus `pixel_block_size`; the worker only forwards a `jpeg` that carries `pixel_block_size`, drops any `raw_jpeg`, and stores nothing but counts + boxes. an older camera build's raw `jpeg` is dropped, and the page says "image hidden for privacy". the r2 frame archive (bucket `lunch-line-frames`, 6.8k frames) and every local raw copy were deleted 2026-11-12; don't bring back raw storage. `.sanity/pixelation_tuner.html` (built by `build_pixelation_tuner.py`) previews block sizes on a stock photo. below the count is a trend chart of the last 90 min (Harrison's 2026-11-11 algorithm note): faint dots = each ~2 s history row, bold line = trailing 2 min time-window mean (trailing so the right edge is the current estimate), line breaks on gaps >30 s. it loads `/history?hours=1.5` (csv) once, then appends live websocket updates; all in `web/src/page.html` (`renderTrend`, `smoothedReadings`), inline svg, no libraries.

## layout
- `detect_people.py`: mac webcam viewer + the shared detection functions (`load_model`, `detect_people`, `draw_people`).
- `stream_people.py`: capture -> detect -> websocket push. `--source arducam` on the pi, `--source webcam --camera N` anywhere (how the whole pipeline is tested without the pi).
- `pi/`: arducam driver (`arducam_mini_2mp_plus.py`, `ov2640_registers.py`), `setup.sh` (run on the pi), `deploy.sh user@host` (run from the mac: rsync + setup), systemd unit.
- `web/`: cloudflare worker `lunch-line-monitor` on route `nuevasocratica.com/lunch-line-monitor*` (account b5767c459ae1102e08c8dd559b76ee15). one durable object `LunchLine` fans updates out over hibernatable websockets: camera -> `/lunch-line-monitor/ingest` (Bearer INGEST_TOKEN), browsers -> `/lunch-line-monitor/live`. latest update is memory-only, so a redeploy shows "waiting for the camera" until the next update. history: the durable object writes one row (time, count, boxes) per ~2 s to its sqlite table `history` (~43k rows/day, under the free plan's 100k rows written/day); export via `GET /lunch-line-monitor/history?hours=N` (csv, pacific time) or `&format=json` (adds boxes). rows from 2026-10-22 16:13-16:14 PT are a mac-webcam test, not the lunch line. 2026-11-05 15:20-15:49 PT is the first real pi session (2311 frames, an indoor common area mid-afternoon, so not lunch traffic): the first ~3.5 min are setup (blank/wall), the last frames show the camera being picked up. public api (Harrison 2026-11-19): `GET /lunch-line-monitor/api/count` (json: count, count_computed_at, count_age_seconds, image_captured_at, image_age_seconds, image_url, pixel_block_size, cpu_temperature_celsius) and `GET /lunch-line-monitor/api/image.jpg` (the latest 14 px pixelated jpeg, never raw), both cors `*` + no-store, 503 if the camera sent nothing for 5 s. the worker reads the latest update by opening a viewer websocket to the durable object and taking the first message, not an rpc method: a new object method 1101'd for minutes after deploy while the camera held the old object open. feedback (Harrison 2026-11-12): anonymous box on the page -> `POST /lunch-line-monitor/feedback {"message"}` (1-2000 chars, stores only time + text in the durable object's `feedback` table); read it all with `curl -H "Authorization: Bearer $INGEST_TOKEN" https://nuevasocratica.com/lunch-line-monitor/feedback`. each submission is also posted (after it is stored, via `ctx.waitUntil`) as an embed with no allowed mentions to #feedback in the socratica discord through the channel webhook 'socratica feedback' (worker secret `DISCORD_FEEDBACK_WEBHOOK_URL`, 1password 'socratica discord feedback webhook'; Harrison 2026-11-14). a webhook, not a bot: resetting a bot token needs his discord security key, which headless camoufox can't provide. failures only show in worker logs (`wrangler tail`). gotcha: a deploy does not immediately restart the live durable object while the camera websocket holds it open, so the worker can be on new code while the object is still old: on 2026-11-12 the old object kept writing to r2 ~5 min after a 100% deploy, and new object methods fail with "The RPC receiver does not implement the method" (1101) until it restarts. test worker changes locally with `npx wrangler@4.152.0 dev --local` + `web/.dev.vars` (the global wrangler 4.86 runtime only supports compatibility dates up to 2026-05-03); local dev rewrites request urls to the route's host, so never build absolute urls from `url.origin`.

## facts
- wiring (verified against arducam docs, 2026-10-08): CS 24 (CE0), MOSI 19, MISO 21, SCK 23, GND 6, SDA 3, SCL 5, **VCC on pin 1 (3.3V), not pin 2**: the board's level-shifter pull-ups likely go to VCC, which would put 5V on pi GPIO (no schematic found; arducam's own pi guide uses 3.3V).
- driver facts + sources: `.sanity/arducam_research.md` (not committed). spi mode 0 at 4 MHz (8 MHz unreliable in the field). frames are read in 4095-byte bursts (py-spidev caps a transfer at 4096 even with a larger kernel bufsiz), each re-sending 0x3C; verified on hardware 2026-10-08. no fixed dummy byte on the plus; the jpeg is cut from FFD8 to the next FFD9. chunked reads (re-send 0x3C per chunk) are also endorsed by arducam staff if the bufsiz route ever fails.
- verified on the real pi 4 (2026-10-08): selftest 16.9 KB jpeg at 640x480 in 0.27 s; service ~0.8 s/frame. reach the pi via `ssh lunchline@lunchline.local` (usb-c gadget cable or Nueva-Guest wifi) or connect.raspberrypi.com (device 'lunchline'). remote shell from the mac, headless (verified 2026-11-16): Raspberry Pi ID = harrisonqian0@gmail.com, 1Password "Raspberry Pi ID (connect.raspberrypi.com)" (xd6fp7v3yiic2jwexfhxlwx5ha). `python3 ~/.sleepbot-brain-slack/tools/browse.py -p rpi open https://connect.raspberrypi.com/devices` -> device row "Connect via" -> "Remote shell" opens a new tab (`tab 1`, url .../devices/894b9ece-a2d0-41bd-b7d5-edc8a3740581/remote-shell-session); `browse.py -p rpi run @.sanity/rpi_connect_shell.py` clicks `.xterm-screen`, types `cmd` + Enter and reads `.xterm-rows` innerText until the `__DONE__` marker. the pi has outbound internet (github 200). user lunchline has passwordless sudo.
- density build (2a60e08) deployed to the pi 2026-11-16: dm-count (full vgg19 at 640x480) alone is 16.5 s/frame on the pi 4 cpu, service ~12.3 s/frame total (was ~0.6 s with yolo only). shrinking the density input is the lever if updates need to be faster. since 2026-11-16 21:00 the image and the count are decoupled (Harrison wanted faster updates without cooking the pi, which sat at 82 c and had throttled counting nonstop): the pixelated image + `cpu_temperature_celsius` go out every 1 s, and `BackgroundCounter` counts on 2 torch threads, rests as long as each count took, only starts a count under 68 c (one count adds ~10 c; the bare pi 4 throttles at 80, idles ~68 with no heatsink), and skips frames where <0.5% of the 14 px blocks moved >12 gray levels (recounts anyway after 5 min). measured live: 1 update/s, ~1 recount per few min on the empty night scene, peaks ~79 c. onnxruntime was only 1.18x faster than torch on the pi (11.1 vs 13.2 s), not worth a dependency. the page shows `live · image Ns ago · count from Ns ago` and a small `raspberry pi cpu N°c` line at the bottom. a heatsink/fan case is the real thermal fix. code-only backup of the 10/08 build: `~/lunch_line_monitor.bak-1116` on the pi. `.sanity/pi_run.sh "<cmd>" [poll_iterations]` wraps the remote-shell snippet for arbitrary commands.
- `.sanity/fake_arducam_test.py` runs it plus `--source arducam` against an emulated arduchip/ov2640 serving a real jpeg.
- updates go as fast as capture + detection (~0.6 s on the pi 4 at `--image-size 416`; 640 was 0.9 s, 320 is 0.27 s). still inside cloudflare's free tier: websocket messages bill 20:1, and a durable object awake 24h is ~11k of the 13k free GB-s/day. don't raise the rate without checking the plan.
- linux torch comes from the pytorch cpu index (`tool.uv.sources`); pypi's linux wheels drag in cuda. verified resolution for aarch64: torch 2.14.1+cpu, no nvidia libraries besides the pure-python nvidia-ml-py.
- measured 2026-10-08: ~0.12-0.15 s per frame end-to-end on the mac (mps).
- counting (11/16): yolo topped out ~10 and anti-correlated with crowd size on shanghaitech b (pearson -0.32); bigger yolo/lower confidence/tiling didn't fix it. the pi now runs only dm-count (crowd_count.py, pearson 0.97 on the same frames, eval in .sanity/crowd_eval) and sends `people: []`; the page shows no boxes.
