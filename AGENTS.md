# lunch_line_monitor

camera -> person detection (YOLO26n) -> live count + box positions on https://nuevasocratica.com/lunch-line-monitor. target hardware: raspberry pi + arducam mini 2mp plus (OV2640, spi + i2c). each update is `{count, people:[{box, confidence}], frame_width, frame_height, jpeg (base64)}`; the page shows the live frame with boxes (changed from faceless figures on 2026-10-08 at Harrison's request).

## layout
- `detect_people.py`: mac webcam viewer + the shared detection functions (`load_model`, `detect_people`, `draw_people`).
- `stream_people.py`: capture -> detect -> websocket push. `--source arducam` on the pi, `--source webcam --camera N` anywhere (how the whole pipeline is tested without the pi).
- `pi/`: arducam driver (`arducam_mini_2mp_plus.py`, `ov2640_registers.py`), `setup.sh` (run on the pi), `deploy.sh user@host` (run from the mac: rsync + setup), systemd unit.
- `web/`: cloudflare worker `lunch-line-monitor` on route `nuevasocratica.com/lunch-line-monitor*` (account b5767c459ae1102e08c8dd559b76ee15). one durable object `LunchLine` fans updates out over hibernatable websockets: camera -> `/lunch-line-monitor/ingest` (Bearer INGEST_TOKEN), browsers -> `/lunch-line-monitor/live`. latest update is memory-only, so a redeploy shows "waiting for the camera" until the next update. history: the durable object writes one row (time, count, boxes) per ~2 s to its sqlite table `history` (~43k rows/day, under the free plan's 100k rows written/day); export via `GET /lunch-line-monitor/history?hours=N` (csv, pacific time) or `&format=json` (adds boxes). rows from 2026-10-22 16:13-16:14 PT are a mac-webcam test, not the lunch line. frames: every camera update's raw (unblurred) jpeg (~1.6/s from the pi, ~17 KB each) goes to r2 bucket `lunch-line-frames` as `<pacific date>/<unix ms>.jpg` with count + boxes in custom metadata; the ~2 s history rows still point at one of them via `frame`. `GET /lunch-line-monitor/frames?day=YYYY-MM-DD[&cursor=]` lists a day (100 per page); `GET /lunch-line-monitor/frames/<key>` needs `Authorization: Bearer INGEST_TOKEN` (the live view is public, the archive is not). bulk download: `uv run download_frames.py --hours N --output-directory DIR` (writes frames.jsonl with boxes; skips files it already has). cost if the pi streams 24/7: ~138k r2 writes/day (~4M/month, ~$14/month past the free 1M) and ~2.3 GB/day of storage (~$0.015/GB-month past the free 10 GB). test worker changes locally with `npx wrangler@4.152.0 dev --local` + `web/.dev.vars` (the global wrangler 4.86 runtime only supports compatibility dates up to 2026-05-03); local dev rewrites request urls to the route's host, so never build absolute urls from `url.origin`.

## run / verify
- mac end-to-end: `LUNCH_LINE_INGEST_TOKEN=$(op item get s5ty2d52vyc33b46kwfpi3kzfq --fields label=lunchline_ingest_token --reveal) uv run stream_people.py --source webcam --camera 1 --save-annotated .sanity/x.png`, then open the page. camera index moves around (iPhone continuity camera can take index 0 and return no frames); the MacBook camera was index 1 on 2026-10-08.
- deploy worker: `cd web && CLOUDFLARE_API_TOKEN=<1P 'Cloudflare API token' field full_token> CLOUDFLARE_ACCOUNT_ID=b5767c459ae1102e08c8dd559b76ee15 wrangler deploy`. `curl` websocket checks need `--http1.1` (over h2 the Upgrade header is dropped and the worker answers 426).
- pi: `./pi/deploy.sh user@host`, reboot, then `uv run python -m pi.arducam_mini_2mp_plus --selftest /tmp/arducam-test.jpg`, then `journalctl -u lunch-line-monitor -f`. `/tmp/lunch-line-latest.jpg` on the pi is the latest annotated frame, for aiming the camera.

## facts
- wiring (verified against arducam docs, 2026-10-08): CS 24 (CE0), MOSI 19, MISO 21, SCK 23, GND 6, SDA 3, SCL 5, **VCC on pin 1 (3.3V), not pin 2**: the board's level-shifter pull-ups likely go to VCC, which would put 5V on pi GPIO (no schematic found; arducam's own pi guide uses 3.3V).
- driver facts + sources: `.sanity/arducam_research.md` (not committed). spi mode 0 at 4 MHz (8 MHz unreliable in the field). frames are read in 4095-byte bursts (py-spidev caps a transfer at 4096 even with a larger kernel bufsiz), each re-sending 0x3C; verified on hardware 2026-10-08. no fixed dummy byte on the plus; the jpeg is cut from FFD8 to the next FFD9. chunked reads (re-send 0x3C per chunk) are also endorsed by arducam staff if the bufsiz route ever fails.
- verified on the real pi 4 (2026-10-08): selftest 16.9 KB jpeg at 640x480 in 0.27 s; service ~0.8 s/frame. reach the pi via `ssh lunchline@lunchline.local` (usb-c gadget cable or Nueva-Guest wifi) or connect.raspberrypi.com (device 'lunchline'). user lunchline has passwordless sudo.
- `.sanity/fake_arducam_test.py` runs it plus `--source arducam` against an emulated arduchip/ov2640 serving a real jpeg.
- updates go as fast as capture + detection (~0.6 s on the pi 4 at `--image-size 416`; 640 was 0.9 s, 320 is 0.27 s). still inside cloudflare's free tier: websocket messages bill 20:1, and a durable object awake 24h is ~11k of the 13k free GB-s/day. don't raise the rate without checking the plan.
- linux torch comes from the pytorch cpu index (`tool.uv.sources`); pypi's linux wheels drag in cuda. verified resolution for aarch64: torch 2.14.1+cpu, no nvidia libraries besides the pure-python nvidia-ml-py.
- measured 2026-10-08: ~0.12-0.15 s per frame end-to-end on the mac (mps).
- known weakness: tightly overlapping people (exactly a lunch line) can merge into one box -> undercount. bigger model (`--model models/yolo26s.pt`) or lower `--confidence` is the first lever.
- `.sanity/` = one-off verify artifacts (contains photos of people, never commit) + a camoufox file-driven browser repl.
