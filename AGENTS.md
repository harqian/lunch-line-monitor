# lunch_line_monitor

camera -> person detection (YOLO26n) -> live count + box positions on https://nuevasocratica.com/lunch-line-monitor. target hardware: raspberry pi + arducam mini 2mp plus (OV2640, spi + i2c). each update is `{count, people:[{id, box, confidence}], frame_width, frame_height, jpeg (base64), regions:{people:[per region], rightward_per_minute:[per boundary], leftward_per_minute:[per boundary], smoothing_seconds, average_people:[per region], seconds_in_region:[per region|null], pace_wait_seconds|null, queued_people, served_per_minute|null, queue_wait_seconds|null, wait_seconds|null, line_direction|null}}`; the page shows the live frame with boxes (changed from faceless figures on 2026-10-08 at Harrison's request), each colored and labeled by its tracked person id.

## layout
- `detect_people.py`: mac webcam viewer + the shared detection functions (`load_model`, `detect_people`, `draw_people`).
- `track_people.py`: `PeopleTracker` gives each person an id across frames (cheapest-first match on center movement / box height + size change; unmatched detections get new ids; unmatched tracks are hidden and dropped after 4 missed frames). `person_color_bgr` uses the same golden-angle hue as `personColor` in `web/src/page.html`; keep them in sync.
- `regions.py` + `lunch_line.toml`: splits the frame into `regions.count` equal vertical regions (5 for now); people per region by box-center x, and per-boundary crossing rates (a tracked id changing region, with hysteresis), all as exponential running averages (`smoothing_seconds`). `wait_seconds` = walking time (per region: person-seconds / distance moved, from people *not* queued, summed over regions with nobody queued now) + queue time (people queued now / crossings into the front region per second while someone queued waits there). queued = own pace slower than `queued_if_slower_than_seconds` to cross the frame. people-in-view / crossings-per-second was tried first and is wrong for sparse crowds (~300 s for one 7 s walker); pace alone lags a growing line. simulated: lone walker 7.0 s exact; queue building 37 s vs 41 actual, draining 13 vs 11; slow-moving full line 34 vs 40. reads low while a line forms but hasn't reached the front, and when people pause mid-frame (`scenarios/stop_and_go.toml`); bystanders count as queued.
- `simulate_people.py` + `scenarios/*.toml`: hand-made points through the real tracker + regions. interactive window (click/drag people, w/l spawn walkers) or `--script scenario.toml` headless (prints actual time in view vs wait shown on arrival). `--send` pushes to the live page. drawn on the annotated frame (`detect_people.draw_regions`) and over the live frame on the page.
- `stream_people.py`: capture -> detect -> websocket push. `--source arducam` on the pi, `--source webcam --camera N` anywhere (how the whole pipeline is tested without the pi).
- `pi/`: arducam driver (`arducam_mini_2mp_plus.py`, `ov2640_registers.py`), `setup.sh` (run on the pi), `deploy.sh user@host` (run from the mac: rsync + setup), systemd unit.
- `web/`: cloudflare worker `lunch-line-monitor` on route `nuevasocratica.com/lunch-line-monitor*` (account b5767c459ae1102e08c8dd559b76ee15). one durable object `LunchLine` fans updates out over hibernatable websockets: camera -> `/lunch-line-monitor/ingest` (Bearer INGEST_TOKEN), browsers -> `/lunch-line-monitor/live`. latest update is memory-only, so a redeploy shows "waiting for the camera" until the next update.

## facts
- wiring (verified against arducam docs, 2026-10-08): CS 24 (CE0), MOSI 19, MISO 21, SCK 23, GND 6, SDA 3, SCL 5, **VCC on pin 1 (3.3V), not pin 2**: the board's level-shifter pull-ups likely go to VCC, which would put 5V on pi GPIO (no schematic found; arducam's own pi guide uses 3.3V).
- driver facts + sources: `.sanity/arducam_research.md` (not committed). spi mode 0 at 4 MHz (8 MHz unreliable in the field). frames are read in 4095-byte bursts (py-spidev caps a transfer at 4096 even with a larger kernel bufsiz), each re-sending 0x3C; verified on hardware 2026-10-08. no fixed dummy byte on the plus; the jpeg is cut from FFD8 to the next FFD9. chunked reads (re-send 0x3C per chunk) are also endorsed by arducam staff if the bufsiz route ever fails.
- verified on the real pi 4 (2026-10-08): selftest 16.9 KB jpeg at 640x480 in 0.27 s; service ~0.8 s/frame. reach the pi via `ssh lunchline@lunchline.local` (usb-c gadget cable or Nueva-Guest wifi) or connect.raspberrypi.com (device 'lunchline'). user lunchline has passwordless sudo.
- `.sanity/fake_arducam_test.py` runs it plus `--source arducam` against an emulated arduchip/ov2640 serving a real jpeg.
- updates go as fast as capture + detection (~0.6 s on the pi 4 at `--image-size 416`; 640 was 0.9 s, 320 is 0.27 s). still inside cloudflare's free tier: websocket messages bill 20:1, and a durable object awake 24h is ~11k of the 13k free GB-s/day. don't raise the rate without checking the plan.
- linux torch comes from the pytorch cpu index (`tool.uv.sources`); pypi's linux wheels drag in cuda. verified resolution for aarch64: torch 2.14.1+cpu, no nvidia libraries besides the pure-python nvidia-ml-py.
- measured 2026-10-08: ~0.12-0.15 s per frame end-to-end on the mac (mps).
- known weakness: tightly overlapping people (exactly a lunch line) can merge into one box -> undercount. bigger model (`--model models/yolo26s.pt`) or lower `--confidence` is the first lever.
- `.sanity/` = one-off verify artifacts (contains photos of people, never commit) + a camoufox file-driven browser repl.
